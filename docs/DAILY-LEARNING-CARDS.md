## 일반 개념 중심 작성 — 2026-10-22 추가 확정

- 학습일지·교안·프로젝트 안에 저장된 독립적인 학습 글은 **그날 다룰 주제의 근거**다. 저장 장소와 글의 성격을 구분하며, 프로젝트 활동을 보고하는 글은 제외한다. 카드는 시간이 지나도 교안 없이 읽고 다른 문제에 적용할 수 있는 설명이어야 한다.
- 개념마다 **무엇인지 → 어떻게 작동하는지 → 어떤 조건에서 쓰는지**를 짧은 문장과 도식으로 전달한다. 필요한 용어와 기호는 그 자리에서 뜻을 밝혀 둔다.
- 특정 shape·하이퍼파라미터·변수명·모델·데이터 건수가 정의를 대신하지 않게 한다. 먼저 N(데이터 수), D(특성/벡터 차원), k(반환 개수) 같은 일반 관계를 설명한다. 숫자가 이해를 돕는 경우에만 '예시'로 표시한다.
- 코드도 일반 원리를 보여 주는 최소 예제로 쓰며, 입력의 의미와 사전 조건을 설명한다. 원본 코드의 변수나 실행 순서를 알아야만 이해되는 설명을 피한다.
- 라이브러리 API나 모델별 규칙은 해당 이름과 적용 범위를 밝힌다. 예를 들어 E5의 접두사 규칙은 E5의 규칙이며 모든 임베딩의 조건이 아니다.
- 프로젝트 실험 결과·A/B 순위·성과·회고는 제외한다. 공정한 비교, 결측 처리, 지표 해석 같은 일반 원리는 독립적인 학습 내용으로 기록되어 있을 때만 다룬다. 예시가 필요하면 개념을 설명하는 최소 예시로 구분한다.
- 마지막 검수 질문: **이 교안을 처음 보는 사람이 나중에 읽어도 정의·관계·조건을 이해하고 다른 데이터나 모델에 적용할 수 있는가?** 그렇지 않으면 예시 중심 설명을 다시 쓴다.
- 편집 기준은 `editorial_basis: "general-concepts-v1"`로 기록한다. 기존 카드도 수정 시 같은 기준을 적용한다.

## 필수 정확성 검증

1. 노션 스키마와 날짜별 본문을 실제로 읽고 로컬 원문도 확인한다. 빈 페이지와 접근 실패를 구분한다.
2. **모든 개념·도식·코드**를 공식 문서, 원 논문, 공신력 있는 교재 등 1차 자료로 대조한다. 원문에 적혀 있다는 이유만으로 참이라고 간주하지 않는다. 관련 문서의 본문까지 읽고 각 섹션에 직접 뒷받침하는 근거를 연결한다.
3. 수식과 계산, shape 및 축, 입력·출력, 벡터·행렬 관계, 화살표의 방향, 비교 기준과 예외 조건을 확인한다. 흐름이 아닌 항목을 인과·순서 화살표로 묶지 않는다. 텐서 구조 그림의 칸 수가 실제 크기를 나타내지 않으면 구조 도식임을 표시한다.
4. 짧은 예시 코드는 학습 주제의 일반 원리를 보여 주도록 작성하고 입력·조건·문법을 검사한다. 결과를 표시하는 계산은 실행해 확인한다. 라이브러리 동작은 해당 공식 API 문서와 비교한다. 실행하지 않은 라이브러리 예시를 실행 검증했다고 쓰지 않는다.
5. 학습용 수치·점수·실험 예시는 조건과 계산 근거를 확인하며 일반적인 모델 순위나 보편적 인과로 확대하지 않는다. 실행하지 않은 예시는 문서 검증과 실행 검증을 구분한다. 프로젝트 성과·결과 보고는 검증 여부와 관계없이 카드 대상에서 제외한다.
6. 근거가 불충분하거나 충돌하면 확인될 때까지 확정 카드에 넣지 않는다. 핵심 내용의 불확실성은 사용자에게 설명하고, 중요하지 않은 단정은 삭제하거나 정확한 조건으로 제한한다. 확인하지 않은 출처나 측정 결과를 만들지 않는다.
7. `card.json`의 각 섹션에 검증한 주장·도식 관계와 근거 URL을 기록한다. 카드 전체 검증 날짜와 보정 사항도 남긴다. `verified`는 근거 대조를 완료했다는 뜻이며 오류 가능성이 절대 없다는 보증이나 Notion 제품의 인증 상태를 뜻하지 않는다.

## 작업 파일과 데이터

날짜별 `workspace/daily-cards/YYYY-MM-DD/`에 `card.json`, PNG, `render.json`, `page.md`, `upload.json`, `receipt.json`을 보관한다. 원문은 수정하지 않는다.

```json
{
  "date": "YYYY-MM-DD",
  "title": "짧은 주제",
  "summary": "하루의 핵심 한 문장",
  "sections": [{
    "title": "개념",
    "body": ["짧고 정확한 핵심 문장"],
    "visual": {
      "type": "compare",
      "items": [
        {"label": "첫 항목", "detail": "짧은 역할", "icon": "vector"},
        {"label": "둘째 항목", "detail": "짧은 역할", "icon": "document"}
      ],
      "caption": "필요할 때만 덧붙이는 조건"
    },
    "verification": {
      "claim": "검증한 설명과 도식 관계",
      "sources": [{"title": "직접 읽은 1차 자료", "url": "https://..."}],
      "note": "조건·한계·보정 사항"
    }
  }],
  "remember": "기억할 한 문장",
  "sources": [{"kind": "project", "title": "학습 원문", "ref": "_posts/파일.md", "url": "https://..."}],
  "verification": {"checked_at": "YYYY-MM-DD", "status": "verified", "corrections": []}
}
```

선택적인 코드는 `section.example = {title, code, explanation}`으로 저장한다. `flow`와 `compare`는 2~4개 items를 사용한다. `pairing`의 각 `{label, detail}`은 좌우 대응이며 2~4쌍이다. `matrix`는 `{type, shape: [2,3], labels: ["행 2", "열 3"], caption}`이다. `curve.function`은 `relu`, `sigmoid`, `tanh`, `quadratic` 중 하나이며 실제 함수로 그린다.

## 생성과 검수

1. 공통 명령: `python -B tools/render_daily_card.py workspace/daily-cards/YYYY-MM-DD/card.json`.
2. 렌더러는 검증 상태·섹션별 근거·필수 도식·코드 문법·이미지 내 URL·텍스트 경계를 검사한다. 이 검사는 내용 자체의 정확성 대조를 대신하지 않는다.
3. **모든 완성 이미지**를 열어 글자 깨짐·잘림·겹침과 휴대폰 너비에서의 가독성을 확인한다. 필요하면 개념별 패널도 확대해서 확인한다. 글자/그림이 불일치하면 데이터와 그림을 함께 수정한다.
4. `render.json`에는 디자인 버전, 개념/도식 수, 텍스트 영역, 입력과 이미지의 해시를 기록한다. 카드 수정 후 반드시 다시 렌더링·검수한다.
5. 렌더러 변경은 `python -B -m unittest discover -s tools -p test_daily_card.py`로 필요한 회귀 검사를 실행한다.

## 노션 저장과 확인

1. 보관함을 먼저 읽고 날짜별 기존 페이지를 확인한다. 생성 응답이 불확실하면 재시도 전에 기존 페이지를 찾는다.
2. Notion `create_file_upload`로 PNG별 임시 업로드 URL·헤더를 받는다. 반환 지침대로 `file` 필드의 multipart/form-data POST를 **정확히 한 번** 보낸다. 인증 정보는 출력하거나 파일에 저장하지 않는다.
3. `tools/upload_daily_card.py`로 업로드한다. `suggested_markdown`을 사용해 **실제 업로드된 PNG**를 페이지 맨 위에 삽입한다. 로컬 경로나 임시 미리보기 링크를 사용하지 않는다.
4. 이미지 아래에 날짜, 접힌 텍스트 요약·코드, 학습 원문 출처, 접힌 **개념별 검증 근거와 보정 사항**을 둔다. Notion 내부 자료는 네이티브 멘션, 외부 근거는 링크로 기록한다.
5. 기존 페이지는 최신 본문을 먼저 읽어 필요한 카드 영역을 교체한다. 사용자 메모와 관련 없는 콘텐츠·하위 페이지는 보존한다.
6. 날짜 페이지를 다시 읽어 이미지 블록, 부모 위치, 검증 영역과 날짜를 확인한다. `receipt.json`에 페이지 URL·이미지 식별자·검수 결과를 남긴다. 마지막으로 보관함에서 전체 날짜의 누락과 중복을 확인한다.
7. 완료 장수·기간과 보관함 링크를 보고한다. 자료 접근 실패·미검증 내용·저장 실패가 있으면 해당 범위를 명확히 알린다.

## 프로젝트 공통 적용

`AGENTS.override.md`가 이 문서를 참조한다. 같은 프로젝트의 새 채팅에서는 `데일리 정리 만들어`로 실행한다. 이미 열린 채팅은 오래된 지침을 사용할 수 있으므로 필요한 경우 이 파일을 다시 읽는다. 다른 체크아웃에는 지침·렌더러·폰트가 함께 있어야 한다. 사용자 요청 없이 커밋·푸시하지 않으며 Claude용 지침은 변경하지 않는다.
