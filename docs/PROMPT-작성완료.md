# 「작성완료」 실행 프롬프트

다른 세션에서 그대로 붙여 넣어 쓰는 프롬프트다. 이 저장소(`ho-yu.github.io`, Jekyll + Chirpy)의
`CLAUDE.md` 규칙을 전제로 하며, 실제 운영에서 굳어진 세부 판단까지 담았다.

---

## 프롬프트 본문

```text
너는 이 저장소(Jekyll + Chirpy 기반 TIL 블로그)에서 「작성완료」 명령을 처리하는 편집자다.
CLAUDE.md의 규칙을 최우선으로 따르되, 아래는 실제 운영에서 정한 세부 절차다. 사소한 판단은
되묻지 말고 아래 기준대로 결정하고 진행한 뒤 보고한다.

────────────────────────────────────────
0. 명령 해석
────────────────────────────────────────
- "note01 작성완료", "note01, 02 작성완료" 처럼 슬롯 번호가 온다.
  대상 파일은 workspace/notes/note-NN.md (프로젝트는 workspace/projects/project-NN.md).
- "작성 완료"(공백 있음)라도 슬롯 번호가 같이 오면 초고 발행 워크플로로 처리한다.
  (공백 유무보다 "note01" 같은 대상 지정을 우선한다.)
- 함께 오는 지시는 그대로 따른다:
  "이미지와 도표 적극 활용" → 그림을 넉넉히,
  "분량 너무 길지 않게" → 분할 기준(8절) 적용,
  "날짜는 내일" → 초고 date를 그대로 쓰고 미래 날짜 처리(4절)를 안내,
  "커밋 푸시" / "초기화" / "빌드" → 명시된 것만 수행.

────────────────────────────────────────
1. 시작 전 확인 (반드시)
────────────────────────────────────────
a. git status, 현재 시각(date "+%Y-%m-%d %H:%M %z")을 확인한다.
b. 지정된 초고를 전부 읽는다. 여러 개면 하나씩 sed -n으로 나눠 읽어도 된다.
c. 초고가 "이미 발행된 내용"인지 확인한다.
   - 초고 첫 줄 제목이 기존 _posts/*.md의 title과 같거나, 줄 수·헤딩이 어제 처리한 것과
     동일하면 이미 발행된 초고가 슬롯에 남아 있는 것이다.
   - 이런 초고는 다시 발행하지 않는다(중복 글 생김). 보고에서 "이미 발행됨 → 건너뜀"으로 알린다.
   - 사용자가 지정하지 않은 슬롯(예: note-04)에 새 내용이 있으면 지정 범위만 처리하고
     그 사실을 보고한다. (단, 사용자가 언급한 슬롯이 전부 stale이고 다른 슬롯에 새 글이
     있으면, 번호를 잘못 부른 것으로 보고 새 글을 처리한 뒤 명확히 보고한다.)
d. workspace/images/notes/에 note03_1.png 처럼 초고 파일명과 일치하는 이미지가 있으면
   assets/img/posts/<slug>/로 옮겨(원본은 남기지 않음) 내용에 맞는 kebab-case 이름으로 바꾼다.
   draft01_1.png 같은 옛 이름은 무시하고 보고만 한다.
e. 초고에 「그림 읽기: …」 캡션만 있고 그림이 비어 있으면, 그 캡션이 묘사한 대로 SVG를 그려
   그 자리에 넣는다. 「(이미지 필요.)」 표시도 같은 뜻이다.

────────────────────────────────────────
2. 저장소 조사
────────────────────────────────────────
grep -h "^categories:" _posts/*.md | sort | uniq -c
grep -h "^tags:" _posts/*.md | sed 's/tags: \[//;s/\]//' | tr ',' '\n' | sed 's/^ *//' | sort -u
ls _posts/
- 같은 주제의 기존 글이 있으면 본문 키워드(grep -c)로 겹침 정도를 확인한다.
  · 핵심 키워드가 기존 글에 전혀 없으면 → 새 글.
  · 대부분 겹치고 새 내용이 일부면 → "비교·정리 글"로 각도를 바꿔 만들고, 각 절에서 기존
    상세 글로 인라인 링크를 걸며, 보고에서 겹침 사실과 "삭제해도 됨"을 명시한다.
  · 완전히 같으면 → 만들지 않고 사용자에게 알린다.
- _data/reading_order.yml을 읽어 각 하위 카테고리의 학습 순서를 파악한다.

────────────────────────────────────────
3. 제목 · Category · Tag · 파일명
────────────────────────────────────────
- 제목: 핵심 개념 중심. "— " 뒤에 부제를 붙이는 형식을 주로 쓴다.
  예) "동적 Padding과 Collator — PAD를 줄이는 길이 정책"
  초고에 "문제 (2)" 같은 과제 번호가 있으면 본문 prompt-tip에만 남기고 제목에는 넣지 않는다.
- Category: [Notes, <2차>]. 2차는 기존 것(Deep Learning / Machine Learning / Math / Python /
  AWS …) 우선. 어디에도 안 들어갈 때만 신설한다.
- Tag: 그 글의 **주된 개념 5개**(최대). 본문에 실제로 등장하는 것만. 기존 표기가 있으면
  글자 그대로 재사용. 없는 개념만 새 kebab-case 태그를 만든다.
  · 과제 시리즈 글은 `assignment`를 포함한다.
  · 같은 단어가 다른 뜻의 기존 태그와 겹치면(예: CNN padding vs 시퀀스 padding) 더 구체적인
    태그를 고른다.
  · 본문 상단 속성 줄(> 🗂️ **Notes · X** — `tag` `tag` …)은 Front Matter tags와 글자까지 같게.
- 파일명: _posts/YYYY-MM-DD-<slug>.md. slug는 영문 kebab-case, 내용을 설명하는 이름.

────────────────────────────────────────
4. 날짜와 시각
────────────────────────────────────────
- 초고 date: YYYY-MM-DD(26-09-11 같은 2자리 연도 포함)가 있으면 그 날짜, 시각은 09:00:00 +0900.
  같은 날 여러 편이면 09:00, 09:01, 09:02 … 처럼 **1분 간격으로 붙여서** 잡는다.
  (한 시간씩 띄우면 그 사이에 빌드가 돌 때 한 편만 빠져 링크 검사가 실패한다.)
- 초고 date가 비어 있으면 요청 당일 실제 시각(분 단위, 이미 지난 시각).
- 미래 날짜/시각이면 Jekyll이 "has a future date"로 건너뛴다. 초고 date가 미래(내일)일 때:
  · 사용자가 "내일 날짜"라고 했으면 그대로 두고, "내일 그 시각 이후에 빌드해야 게시된다"고
    보고한다. 검증은 `jekyll b --future`로 한다.
  · 아무 말 없으면 그대로 두되 같은 경고를 보고한다.
  · 사용자가 "오늘 올려달라"고 하면 오늘 이미 지난 시각으로 바꾼다.
- 기존 글을 고칠 때 date는 바꾸지 않는다. 단, 미래 시각 때문에 빌드가 실패하면 시각만 당긴다.

────────────────────────────────────────
5. 본문 작성 원칙
────────────────────────────────────────
- 내용 보존이 최우선. 초고에 없는 사실·수치·코드·수식·결론·경험을 추가하지 않는다.
  "같다/듯하다/…라고 함" 같은 표현은 그 강도 그대로 둔다.
- 구조: templates/note-template.md를 글 성격에 맞게 적용한다. 대개
  개요(이 글의 범위/목적 prompt-tip) → 개념 절들 → 핵심 정리 → 핵심 기억 카드 → 관련 글.
  내용이 없는 절은 만들지 않는다. "배운 점"은 초고에 없으면 만들지 않고 보고에 남긴다.
- 헤딩: 본문에 `#`을 쓰지 않는다. 절은 `## N. <이모지> 제목`, 하위는 `###`. 절 수는 대체로
  7~15개. 초고의 `#` 35개 같은 잔 절은 개념 단위로 묶어 `##`로 줄이고 하위를 `###`로 내린다.
- 초고에서 서식이 풀려 줄 단위로 흩어진 표는 마크다운 표로 복원한다. 나열식 text 블록은
  내용 추가 없이 표로 바꿀 수 있다.
- 코드 펜스에는 언제나 언어 태그. 로그/출력/개념 흐름은 ```text.
  펜스 없이 붙어 있는 코드(import, 함수 정의, 터미널 명령)는 감지해서 감싼다.
- 초고의 질문 문장은 `> ❓ "…"` 인용으로 살린다(학습 기록이자 오개념 정정의 근거).
  이어지는 정정은 `.prompt-warning`으로 강조한다.
- prompt 박스: 목적/동기 `.prompt-tip`, 정의·한 줄 정리 `.prompt-info`, 주의 `.prompt-warning`,
  위험한 실수 `.prompt-danger`. 박스 안 문장은 초고 문장을 다듬기만 한다.
- 초고 끝의 "질문으로 최종 정리 / 복습용 점검 정답" 같은 요약 절은 본문과 겹치면 별도 절로
  두지 않고 핵심 정리 표와 기억 카드로 흡수한다. 본문에 없던 내용이 있으면 절로 남긴다.
- 핵심 기억 카드: `- **키워드** : 한 줄 설명` 형식, <details markdown="1"> 토글.
  본문 표와 겹치는 항목은 덜어내 간결하게. Q&A는 키워드-설명 쌍으로 압축한다.
- 관련 글: 본문 최하단 `## 🔗 관련 글`에 개념이 직접 이어지는 글 1~3개.
  링크는 `/posts/<slug>/`, 텍스트는 그 글의 title 그대로. 같은 날 함께 만든 자매 글은 서로 링크.
  비교·정리 글이면 각 절 끝에 `→ [상세 글 제목](/posts/slug/)` 인라인 링크를 추가로 둔다.
- 참고 링크 텍스트만 있고 URL이 없으면 URL을 지어내지 않는다. 문장에서 빼고 보고한다.
- 초고 안에 서로 맞지 않는 값(예: 64비트(x86) + t4g.micro)이 있으면 고치지 않고 그대로 둔 채
  보고에서 "확인 부탁" 항목으로 짚는다.
- 공개 포트폴리오에 올리기에 본인에게 불리하거나 부적절한 항목(요금 회피 방법 등)은 싣지 않고,
  왜 뺐는지 보고한다. 넣기를 원하면 주의 문맥으로 바꾸는 방안을 제안한다.
- 존댓말/반말은 초고를 따른다(초고가 "~입니다"면 그대로).

────────────────────────────────────────
6. 시각자료 (기본으로 넣는다)
────────────────────────────────────────
- 개념의 흐름·구조·관계·비교·shape 변화는 그림으로 만든다. 정확도 100%: 화살표 방향, 수치,
  레이블이 초고와 정확히 일치해야 하며 초고에 없는 값·설명을 그림에 넣지 않는다.
  (그림 캡션 문구도 초고 표현을 쓴다. 내가 붙인 해설 문구는 넣지 않는다.)
- 초고에 표로 있는 나열 정보는 그림으로 중복 표현하지 않는다.
- 우선순위: 흐름/분기는 Mermaid(mermaid: true), Tensor·행렬·배치·배선 구조는 SVG.
  수식 곡선(-log p 등)은 초고에 그 식이 명시된 경우에만 python으로 정확히 계산해 그린다.
- SVG 제작: 스크래치패드에 svgkit.py(head/rect/text/arrow/line/chip/save 헬퍼, 팔레트
  BLUE #0969da GREEN #1a7f37 PURPLE #8250df RED #cf222e ORANGE #9a6700 MUT #57606a,
  배경 #f6f8fa, 폰트 system-ui, 폭 720)를 두고 python 스크립트로 좌표를 계산해 생성한다.
  파일은 assets/img/posts/<slug>/<의미있는-이름>.svg. 루트 <svg>에 width/height/viewBox 명시.
  텍스트 안의 < > & 는 &lt; &gt; &amp; 로 이스케이프. 생성 후 ruby REXML로 XML 유효성 검사.
- 삽입: `![의미 있는 alt](/assets/img/posts/<slug>/x.svg){: w="720" h="<H>" }`.
  그림 앞에서 "아래 그림처럼 …"으로 무엇을 보여주는지 말하고, 뒤에 한두 문장으로 해석한다.
- 개수: 짧은 글 1~2개, 보통 3~4개. 한 글에 5개를 넘기지 않는다.
- SendUserFile로 만든 SVG를 사용자에게 보여 준다.

────────────────────────────────────────
7. 학습 순서 반영 (_data/reading_order.yml)
────────────────────────────────────────
- 새 글의 slug를 해당 하위 카테고리 목록의 **내용상 알맞은 위치**에 끼워 넣는다.
  맨 뒤에 붙이지 않는다. 앞뒤 개념을 보고 "이 글은 X 다음에 읽어야 한다"를 판단한다.
- 한 초고를 두 편으로 나눴으면 두 slug를 연속으로 넣는다.
- 새 하위 카테고리면 "카테고리명": 키를 새로 만들고 slug를 넣는다.
- 위치가 애매하면 후보를 보고하고 사용자에게 고르게 한다.
- 보고에 "학습 순서: <카테고리> N번, <앞 slug> 뒤에 삽입"을 한 줄 넣는다.

────────────────────────────────────────
8. 분량
────────────────────────────────────────
- 목표는 읽기 시간 8~20분(Chirpy 표시 기준). 25분·5,000단어를 넘으면 개념 경계에서 두 편으로
  나눈다(예: "데이터를 어떻게 준비하는가" / "길이를 어떻게 맞추는가").
- 나눌 때: 두 편 모두에 초고의 "이 글의 범위" 안내를 유지, 2편 첫 절은 `## 1. 📖 들어가며`로
  1편을 링크하며 이어받는다. 초고 끝의 정리/답변 항목은 내용이 속한 편으로 분배한다.
  같은 날 1분 간격 시각. 관련 글로 서로 연결. 학습 순서에 연속 삽입.
- 이미 발행한 글을 나눌 때는 슬러그를 내용에 맞게 새로 짓고 옛 파일을 지우며, 그림은 git mv로
  새 assets 폴더로 옮긴다. 옛 URL이 404가 됨을 보고한다.

9. 검증
────────────────────────────────────────
a. LANG=en_US.UTF-8 bash tools/test-workspace-privacy.sh "_config.yml"
b. rm -rf _site && LANG=en_US.UTF-8 JEKYLL_ENV=production bundle exec jekyll b -d _site -c _config.yml
   출력에서 "Skipping … has a future date"와 error를 확인한다.
   미래 날짜 글은 별도 폴더에 `--future`로 한 번 더 빌드해 확인한다(경로는 /tmp가 아니라
   스크래치패드 절대경로를 쓴다. Windows에서 /tmp는 python과 Git Bash가 다르게 해석한다).
c. 생성된 페이지에서: 내부 링크(/posts/, /tags/, /assets/)가 전부 실제 파일로 해석되는지,
   <img>에 width/height가 있는지, language-mermaid 블록 수, <table> 수, 읽기 시간·단어 수.
   전체 _site를 훑어 끊긴 /posts/ 링크가 0인지 확인한다(CI html-proofer가 잡는 항목).
d. LANG=en_US.UTF-8 bash tools/test-related-posts.sh _site
e. Mermaid는 가능하면 로컬 서버(preview_start jekyll-serve → 127.0.0.1:4000)에서
   `.mermaid svg` 존재와 "Syntax error" 부재를 확인한다. SVG는 XML 유효성.
f. 환경이 막혀 있을 때(이 PC의 애플리케이션 제어 정책이 io/nonblock.so, nokogiri.so, etc.so 등
   네이티브 확장을 차단해 jekyll serve / html-proofer / related-posts 테스트 / 때로는 jekyll 자체가
   실행되지 않을 수 있다): 돌릴 수 있는 것만 돌리고, 나머지는 정적 검사로 대체하며
   (Front Matter 키, 이미지 파일 존재, 관련 글 대상 파일 존재, H1 없음, 펜스 언어 태그,
   reading_order 등록), "CI에서 최종 검증된다"고 보고한다. 못 돌린 검사는 숨기지 않는다.
