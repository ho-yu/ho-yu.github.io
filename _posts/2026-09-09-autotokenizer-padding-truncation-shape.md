## 1. 📖 AutoTokenizer는 무엇을 자동으로 해 주는가?

> 📌 **이 글의 범위** · 텍스트가 모델 입력이 되는 과정부터, 패딩·길이 제한·shape가 필요한
> 이유까지 정리했습니다. 대화에서 직접 질문한 문장과 작성한 답변을 인용했으며, 그림의 토큰과
> 숫자는 실제 실행 결과가 아닌 설명용 예시입니다.
{: .prompt-tip }

> ❓ "autotokenizer에 대해서 자세히 설명해줘."

AutoTokenizer는 사용할 모델의 체크포인트를 보고, 그 모델에 맞는 토크나이저를 선택해 불러오는
클래스입니다. 먼저 세 가지를 구분하면 이해하기 쉽습니다.

| 이름 | 역할 |
| --- | --- |
| **토큰(Token)** | 텍스트를 처리하기 위해 나눈 단위. 반드시 한 글자나 한 단어인 것은 아님 |
| **토크나이저(Tokenizer)** | 텍스트를 토큰으로 나누고, 토큰을 숫자 ID로 바꾸는 도구 |
| **AutoTokenizer** | 모델에 맞는 토크나이저를 자동으로 선택해 불러오는 도구 |

토큰은 모델의 규칙에 따라 단어보다 작은 **서브워드(Subword)** 가 될 수도 있습니다. 여기서는
"띄어쓰기만 기준으로 자르는 것은 아니다"라고 기억하면 충분합니다.

> ⚠️ `Auto`는 **토크나이저 선택**을 자동으로 해 준다는 뜻입니다. 문장을 보고 가장 좋은 모델을
> 고르거나, 실행할 때마다 새로운 토큰 분리 규칙을 학습한다는 뜻은 아닙니다.
{: .prompt-warning }

```python
from transformers import AutoTokenizer

checkpoint = "google-bert/bert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(checkpoint)
```

| 코드 | 의미 |
| --- | --- |
| `from transformers import AutoTokenizer` | Transformers 라이브러리에서 클래스를 가져옴 |
| `checkpoint` | 불러올 모델 자료의 이름을 담은 변수 |
| `from_pretrained(checkpoint)` | 이미 준비된 어휘와 토큰 분리·특수 토큰 설정 등을 불러옴 |
| `tokenizer` | 이후 실제 텍스트를 처리하는 객체 |

**체크포인트(checkpoint)** 는 학습된 모델이나 관련 설정을 저장해 둔 묶음입니다. 이름 대신 로컬
저장 경로를 사용할 수도 있습니다. 위 호출은 토크나이저를 불러오며, 예측을 수행할 모델 가중치는
별도로 불러옵니다.

## 2. 🔗 모델과 토크나이저의 체크포인트를 맞추는 이유

> ❓ "Model과 tokenizer checkpoint를 맞춰야 하는 이유는 무엇인가요?"

모델은 학습할 때 특정한 토큰↔ID 대응 관계를 사용합니다. 토크나이저가 만든 ID가 그 관계와
일치해야 합니다. 가령 A와 B의 어휘 사전이 다음처럼 다르다고 가정해 보겠습니다.

| 토큰 | A 토크나이저의 ID | B 토크나이저의 ID |
| --- | --- | --- |
| 제품 | 350 | 820 |
| 배송 | 820 | 350 |

A와 함께 학습한 모델에 `350`을 넣으면, 모델은 학습 당시 `제품`에 대응하던 임베딩을 참조합니다.
그런데 B로 `배송`을 변환해도 `350`이 나오므로, 이를 그대로 A 모델에 넣으면 서로 다른 내용을
같은 번호로 전달하게 됩니다.

![위쪽은 제품이 A 토크나이저를 거쳐 ID 350이 되고 A 모델에서 제품의 임베딩으로 맞게 연결되는 정상 경로, 아래쪽은 배송을 B 토크나이저가 같은 ID 350으로 바꿔 A 모델이 제품의 임베딩을 참조하게 되는 불일치 경로](/assets/img/posts/autotokenizer-padding-truncation-shape/checkpoint-mismatch.svg){: w="720" h="292" }

따라서 다음 약속이 모델의 학습 당시와 맞아야 합니다.

- 텍스트를 어떤 규칙으로 토큰으로 나누는가?
- 각 토큰은 어떤 ID에 대응하는가?
- 특수 토큰은 무엇이며, 어느 위치에 추가하는가?

여기서 특수 토큰은 문장 경계나 패딩 같은 역할을 표시하는 토큰입니다. 예를 들어 BERT는
`[CLS]`, `[SEP]`, `[PAD]` 등을 사용합니다. 모델마다 사용하는 종류와 규칙은 다릅니다.

> 💡 같은 체크포인트에서 모델과 토크나이저를 불러오는 것이 기본입니다. 본질적인 조건은 이름
> 문자열 자체가 아니라 **학습 당시의 토크나이저 규칙과 호환되는가**입니다. 다른 이름으로 저장된
> 파인튜닝 모델이라도 원래 토크나이저를 그대로 사용했다면 호환될 수 있습니다.
{: .prompt-info }

## 3. ⚙️ `tokenize()`와 `tokenizer(...)`는 무엇이 다른가?

> ❓ "tokenize()와 tokenizer(...)의 목적 차이는 무엇인가요?"

`tokenize()`는 나뉜 토큰을 확인할 때, `tokenizer(...)`는 모델 입력을 준비할 때 사용합니다.

```python
text = "This product is easy to use."

# 어떻게 나뉘었는지 토큰 문자열을 확인
tokens = tokenizer.tokenize(text)

# 숫자 ID와 모델이 요구하는 입력 정보를 생성
encoded = tokenizer(text)
```

| 비교 항목 | `tokenizer.tokenize(text)` | `tokenizer(text)` |
| --- | --- | --- |
| 주요 결과 | 토큰 문자열 리스트 | `input_ids` 등을 담은 딕셔너리처럼 접근 가능한 객체 |
| 주된 목적 | 토큰 분리 결과 관찰 | 실제 모델 입력 준비 |
| ID 변환 | 별도 메서드로 수행 | 함께 수행 |
| 모델용 특수 토큰 추가 | 이 단계만으로 입력 구성이 완성되지는 않음 | 모델 설정과 옵션에 따라 추가 |
| 패딩·잘라내기·텐서 변환 | 이 메서드의 주된 역할이 아님 | 옵션으로 지정 |

`tokenizer(text)`는 객체를 함수처럼 호출하는 파이썬 문법입니다. 텍스트 하나나 여러 개를 전달할
수 있습니다. 패딩은 기본적으로 자동 적용되는 것이 아니라 `padding` 옵션으로 요청합니다.

처리 과정을 나눠 확인할 때는 다음 메서드도 사용할 수 있습니다.

```python
# 분리한 토큰 문자열들을 ID로 변환
token_ids = tokenizer.convert_tokens_to_ids(tokens)

# ID를 텍스트로 변환하되, 특수 토큰은 표시하지 않음
decoded_text = tokenizer.decode(token_ids, skip_special_tokens=True)
```

소문자 변환이나 공백 처리 등이 적용되었다면 `decode()`의 결과가 원본 문장과 완전히 같지는 않을
수 있습니다.

반환값의 대표적인 키는 다음과 같습니다.

| 키 | 담고 있는 정보 |
| --- | --- |
| `input_ids` | 입력 토큰을 정수 ID로 변환한 결과 |
| `attention_mask` | 패딩처럼 어텐션에서 참조하지 않을 위치를 구분하는 정보 |
| `token_type_ids` | BERT 같은 일부 모델에서 입력의 첫 번째·두 번째 문장 구간 등을 구분하는 정보 |

모든 모델이 위 키를 전부 사용하는 것은 아닙니다. 특히 `token_type_ids`는 반환되지 않는 경우가
있습니다.

### 토큰 ID는 임베딩 벡터와 다르다

`제품 → 350`이라면 `350`은 토큰을 가리키는 번호입니다. 이 숫자 자체가 `제품`의 의미를 담은
벡터는 아닙니다.

```text
토크나이저 → 토큰을 정수 ID로 변환
임베딩 층  → 각 ID에 대응하는 벡터를 가져옴
이후 층    → 벡터들을 처리하며 문맥을 반영
```

ID가 `820`이라고 해서 `350`보다 중요하거나 의미가 더 크다는 뜻은 아닙니다.

## 4. 📦 패딩과 길이 제한을 사용하는 이유

> ❓ "여러문장을 한번에 처리할 때, 패딩과 길이제한을 자주 사용하는 이유가 뭔지도 알려줘."

한 번에 처리하는 입력 묶음을 **배치(batch)** 라고 합니다. 리뷰 3개를 한 번에 처리하면 배치
크기가 3입니다. 패딩과 잘라내기는 서로 다른 문제를 해결합니다.

| 작업 | 하는 일 | 목적 |
| --- | --- | --- |
| **패딩(Padding)** | 짧은 입력에 PAD 토큰을 추가 | 같은 배치의 입력 길이를 맞춤 |
| **잘라내기(Truncation)** | 설정한 길이를 넘는 입력을 자름 | 입력 한도와 계산량을 관리 |

### 패딩과 `attention_mask`

토큰 길이가 3, 5, 2인 리뷰를 하나의 일반적인 텐서로 묶으려면, 각 행의 길이를 같게 만듭니다.
가장 긴 리뷰에 맞추면 모두 5칸이 됩니다.

![리뷰 A·B·C의 input_ids가 각각 토큰 3·5·2개이고 부족한 자리를 PAD로 채워 [3, 5] 모양이 되며, 아래 attention_mask에서 입력 위치는 1, 패딩 위치는 0으로 표시되는 그림](/assets/img/posts/autotokenizer-padding-truncation-shape/padding-and-mask.svg){: w="720" h="362" }

모양이 일정하면 여러 문장을 묶어서 GPU 등의 장치에서 계산하기 편해집니다. 패딩은 문장의 의미를
보충하는 것이 아니라 배열에 필요한 자리를 채우는 작업입니다.

| 값 | 이 배치 예시에서의 의미 |
| --- | --- |
| `1` | 실제 입력 위치. 모델에 필요한 특수 토큰도 포함 |
| `0` | 패딩 위치. 어텐션에서 참조하지 않도록 표시 |

> ⚠️ 이 값은 단어 중요도 점수가 아닙니다. 또한 마스크를 사용해도 일반적인 밀집 텐서 계산에서
> 패딩의 메모리·연산 비용이 모두 사라지는 것은 아닙니다.
{: .prompt-warning }

### 길이 제한 — 너무 긴 입력의 부담을 관리한다

1. **모델의 입력 한도** — 모델이 지원하는 최대 길이를 넘지 않도록 합니다.
2. **계산량과 메모리** — 긴 입력일수록 처리 부담이 커집니다.
3. **배치의 패딩 낭비** — 아주 긴 리뷰 하나 때문에 나머지 짧은 리뷰도 길게 패딩되는 상황을
   줄입니다.

예를 들어 길이가 20, 30, 1,000인 리뷰를 최장 길이에 맞추면 모두 1,000칸이 됩니다. 앞의 두
리뷰는 대부분이 패딩입니다.

일반적인 전체 셀프 어텐션에서는 길이가 `L`일 때 토큰 간 점수의 수가 `L²`에 비례합니다.

| 토큰 길이 `L` | 토큰 간 점수의 수 `L²` |
| --- | --- |
| 128 | 16,384 |
| 256 | 65,536 |
| 512 | 262,144 |

길이가 2배면 이 부분의 토큰 쌍 수는 4배가 됩니다. 모델 전체 실행 시간이 반드시 정확히 4배가
된다는 뜻은 아닙니다.

> ⚠️ 다만 잘라내면 정보가 사라질 수 있습니다. 리뷰 끝의 "그런데 며칠 쓰니 고장 났어요"가
> 잘리면 감성 분류에 필요한 단서를 잃습니다.
{: .prompt-warning }

길이는 실제 토큰 길이 분포, 중요한 내용의 위치, 모델 한도와 메모리를 고려해 정합니다. 긴 내용을
보존해야 하면 여러 구간으로 나누어 처리할 수도 있습니다.

## 5. 📐 왜 배열의 모양을 맞춰야 하는가?

> ❓ "왜 배열의 모양을 맞춰야 하고, 어떤 규칙때문에 배열을 맞추는거야?"

여기에는 텐서의 모양에 관한 조건과 행렬 연산의 차원 조건이 있습니다. 서로 연결되지만 같은
조건은 아닙니다.

### 조건 A — 일반적인 밀집 텐서는 각 축의 크기가 일정하다

머신러닝에서 텐서는 숫자를 여러 차원의 배열로 담는 자료구조라고 이해하면 됩니다. 파이썬
리스트는 길이가 다른 리스트들을 담을 수 있습니다.

```python
reviews = [
    [11, 12, 13],
    [21, 22, 23, 24, 25],
    [31, 32]
]
```

그러나 이 데이터를 하나의 일반적인 2차원 텐서로 만들려면 모양을 `[행 수, 열 수]`로 표현할 수
있어야 합니다. 행은 3개이지만, 열은 3개·5개·2개로 다릅니다. 패딩으로 모두 5칸으로 맞추면
`[3, 5]`라는 하나의 모양이 정해집니다.

> 💡 자연어의 규칙이 아니라 **여러 입력을 같은 텐서에 담는 방식**에서 오는 조건입니다.
{: .prompt-info }

### 조건 B — 행렬 곱셈에서는 곱하는 두 차원이 맞아야 한다

```text
(m, n) @ (n, p) → (m, p)
```

앞 행렬의 열 수 `n`과 뒤 행렬의 행 수 `n`이 같아야 합니다. 예를 들어 임베딩 결과가 `[3, 5, 4]`
이고 가중치가 `[4, 8]`이면, 각 토큰의 4차원 벡터를 8차원 벡터로 변환할 수 있습니다. 결과는
`[3, 5, 8]`입니다.

| 구분 | 이 예시에서 맞추는 것 | 이유 |
| --- | --- | --- |
| 패딩 | 각 샘플의 토큰 길이를 5로 통일 | 하나의 배치 텐서로 묶기 위해 |
| 행렬 곱셈 | 임베딩의 마지막 차원 4와 가중치의 첫 차원 4 | 벡터에 가중치 행렬을 곱하기 위해 |

문장 길이를 임베딩 차원이나 가중치 차원과 같게 만들 필요는 없습니다. 이 예시에서도 토큰 길이는
5이고 임베딩 차원은 4입니다.

문장을 하나씩 처리한다면 `[1, 3]`, `[1, 5]`, `[1, 2]`처럼 호출마다 길이가 달라도 됩니다. 길이가
다른 입력을 처리하는 특수한 구현도 있지만, 이 노트에서는 일반적인 밀집 배치를 기준으로
설명합니다.

## 6. 🔢 shape 읽기와 임베딩

> ❓ "위 작업이 shape를 맞추는 작업인거지?"

맞습니다. 패딩은 배치로 묶을 입력들의 shape를 맞추는 방법입니다. shape는 각 축의 크기를
순서대로 나타낸 정보입니다. 축(axis)은 데이터를 바라보는 방향 또는 구분 기준이라고 이해하면
됩니다.

> ❓ "input_ids [4, 12]의 두 축은 무엇인가요?"

| 축 | 값 | 의미 |
| --- | --- | --- |
| 첫 번째 축 | 4 | 배치의 입력 샘플 수 |
| 두 번째 축 | 12 | 각 샘플의 최종 토큰 길이 |

리뷰 한 개를 샘플 하나로 넣었다면 "리뷰 4개, 각 12칸"입니다. 샘플 하나가 문장 쌍으로 구성될
수도 있으므로 문장 수보다 **샘플 수**라는 표현이 더 정확합니다.

`12`에는 추가된 특수 토큰과 패딩도 포함됩니다. 원래 길이가 모두 12였다면 패딩 없이도 같은
shape가 나옵니다.

> ⚠️ `input_ids`의 **값**이 `[4, 12]`인 것과 **shape**가 `[4, 12]`인 것은 다릅니다. 전자는 ID
> 두 개이고, 후자는 배열 크기를 설명합니다.
{: .prompt-warning }

### 임베딩을 거치면 축이 하나 추가된다

![왼쪽은 샘플 A·B·C 3개 × 토큰 5칸의 input_ids [3, 5], 오른쪽은 그중 A 샘플 하나를 확대해 각 토큰이 d1부터 d4까지 4차원 벡터로 바뀐 모습이며 전체 결과가 [3, 5, 4]가 되는 그림](/assets/img/posts/autotokenizer-padding-truncation-shape/embedding-adds-axis.svg){: w="720" h="330" }

| 데이터 | shape | 해석 |
| --- | --- | --- |
| `input_ids` | `[B, L]` | 샘플 B개 × 토큰 L칸 |
| `attention_mask` | `[B, L]` | 각 토큰 위치와 대응되는 마스크 |
| 임베딩 결과 | `[B, L, D]` | 각 토큰을 D차원 벡터로 표현 |

예를 들어 `input_ids`가 `[4, 12]`이고 임베딩 차원이 768이면, 임베딩 결과는 `[4, 12, 768]`
입니다.

### `padding`과 `reshape`는 서로 다른 작업이다

| 작업 | 무엇을 바꾸는가? | 원소 수 |
| --- | --- | --- |
| 패딩 | PAD 값을 추가해 길이를 맞춤 | 추가한 만큼 증가 |
| 잘라내기 | 일부 토큰을 제거해 길이를 제한 | 잘라낸 만큼 감소 |
| `reshape` | 기존 원소를 다른 모양으로 해석 | 유지 |

예를 들어 원소 6개는 `[2, 3]`에서 `[3, 2]`로 reshape할 수 있습니다. 하지만 길이가 다른 문장들을
올바르게 패딩하는 작업을 reshape만으로 대신할 수는 없습니다.

전체 데이터셋의 모든 배치를 같은 길이로 맞출 필요는 없습니다. 같은 텐서로 묶는 입력끼리 맞추면
되므로, 이번 배치는 `[4, 12]`, 다음 배치는 `[4, 20]`이어도 모델이 지원하는 범위 안에서 처리할
수 있습니다.

## 7. 🧪 코드의 패딩·길이 옵션 연결하기

```python
texts = [
    "Good product.",
    "This product is very easy to use."
]

batch = tokenizer(
    texts,
    padding=True,
    truncation=True,
    max_length=128,
    return_tensors="pt"
)
```

| 설정 | 하는 일 |
| --- | --- |
| `texts` | 문자열 리스트를 배치로 전달 |
| `padding=True` | 처리된 입력 중 가장 긴 길이에 맞춰 패딩 |
| `truncation=True` | 지정한 최대 길이를 넘으면 잘라냄 |
| `max_length=128` | 여기서는 특수 토큰을 포함해 최대 128토큰으로 제한 |
| `return_tensors="pt"` | 결과를 PyTorch 텐서로 반환 |

길이 관점에서는 **길이 제한을 적용한 뒤, 같은 배치에서 가장 긴 입력에 맞춘다**고 이해하면
됩니다. 다음 표의 원래 길이는 특수 토큰까지 포함한 길이입니다.

| 원래 길이 | 제한 적용 후 | 패딩 후 |
| --- | --- | --- |
| 20, 70, 200 | 20, 70, 128 | 128, 128, 128 |
| 20, 50, 70 | 20, 50, 70 | 70, 70, 70 |

> ⚠️ `padding=True`와 `max_length=128`을 함께 쓴다고 무조건 128칸으로 채우지는 않습니다. 항상
> 128칸으로 맞추려면 `padding="max_length"`를 사용합니다. `max_length`만 지정하고 잘라내기를
> 켜지 않으면, 긴 입력이 자동으로 잘리는 것도 아닙니다.
{: .prompt-warning }

## 8. 🧯 `token_type_ids`가 없는 모델도 처리하는 방법

> ❓ "token_type_ids가 없는 모델에서도 코드가 동작하게 하려면 어떻게 해야 하나요?"

특정 키가 항상 있다고 가정하지 않으면 됩니다. 반환된 입력과 shape를 확인할 때는 실제로 존재하는
키를 순회합니다.

```python
for key, value in batch.items():
    print(key, value.shape)
```

`items()`는 딕셔너리의 키와 값을 한 쌍씩 가져옵니다. 특정 값이 필요할 때는 존재 여부부터
확인합니다.

```python
if "token_type_ids" in batch:
    print(batch["token_type_ids"])
```

모델과 토크나이저가 맞고 `batch`에 모델이 받는 입력만 들어 있다면, 다음처럼 전달할 수 있습니다.

```python
outputs = model(**batch)
```

`**batch`는 딕셔너리 항목을 이름 있는 인자로 풀어 전달합니다. `batch`에 `input_ids`와
`attention_mask`만 있다면 다음 호출과 같습니다.

```python
outputs = model(
    input_ids=batch["input_ids"],
    attention_mask=batch["attention_mask"]
)
```

없는 `token_type_ids`를 임의로 만들어 추가할 필요는 없습니다.

> ⚠️ 단, `**batch`가 모델이 받지 않는 키까지 알아서 제거해 주지는 않으므로, 분석용 부가정보를
> 넣었다면 모델 입력과 구분해야 합니다.
{: .prompt-warning }

## 9. ✅ 내가 작성한 답변과 정확한 표현

질문 순서대로 직접 작성한 답변입니다.

1. 전자는 분할 관찰용 token 문자열, 후자는 batch와 mask를 포함한 실제 모델 입력 생성에
   적합합니다.
2. 문장 4개와 padding 후 길이 12입니다.
3. 반환된 key를 순회하거나 `if "token_type_ids" in batch`로 조건 처리합니다.
4. 같은 ID가 같은 token과 special token 규칙을 가리켜야 하기 때문입니다.

네 답변 모두 핵심을 이해한 답입니다. 복습할 때는 다음처럼 표현을 다듬어 기억하면 정확합니다.

| 항목 | 기억할 답변 |
| --- | --- |
| 1. 두 호출의 목적 | `tokenize()`는 토큰 문자열 관찰, `tokenizer(...)`는 모델 입력 준비. 배치·패딩·텐서 변환은 입력과 옵션에 따라 적용 |
| 2. `[4, 12]`의 축 | 배치의 입력 샘플 4개, 샘플마다 최종 토큰 길이 12. 패딩이 있었다고 단정할 수는 없음 |
| 3. 선택적인 키 처리 | 실제 반환된 키를 순회하거나 존재 여부를 확인. 호환되는 모델에는 모델 입력만 담은 batch를 `**batch`로 전달 가능 |
| 4. 체크포인트 호환 | 토큰 분리, 토큰↔ID 매핑, 특수 토큰 규칙이 학습 당시와 일치해야 함 |

## 10. 🧠 핵심 기억 카드

<details markdown="1">
<summary><strong>펼쳐서 확인</strong></summary>

- **AutoTokenizer** : 체크포인트를 보고 그 모델에 맞는 토크나이저를 선택해 불러오는 클래스
- **`Auto`의 의미** : 토크나이저 **선택**이 자동 — 좋은 모델을 고르거나 분리 규칙을 학습하지 않는다
- **체크포인트를 맞추는 이유** : A에서 `제품=350`이어도 B에서는 `배송=350`일 수 있다
- **본질적인 조건** : 이름 문자열이 아니라 **학습 당시 토크나이저 규칙과 호환되는가**
- **주요 키** : `input_ids` / `attention_mask` / `token_type_ids` (모두 반환되지는 않음)
- **ID ≠ 임베딩 벡터** : ID는 번호, 벡터는 임베딩 층이 가져온다 — 820이 350보다 중요하지 않다
- **패딩** : 짧은 입력에 PAD 추가 → 같은 배치의 길이를 맞춤
- **잘라내기** : 설정 길이를 넘는 입력을 자름 → 입력 한도와 계산량 관리
- **`attention_mask`** : `1`은 입력 위치(특수 토큰 포함), `0`은 패딩 위치 — 중요도 점수가 아니다
- **`L²`** : 128→16,384, 256→65,536, 512→262,144 — 길이 2배면 토큰 쌍 4배
- **shape를 맞추는 조건 B** : `(m, n) @ (n, p) → (m, p)` — 곱하는 두 차원이 같아야 한다
- **shape 읽기** : `input_ids [4, 12]` = 샘플 4개 × 최종 토큰 길이 12 (특수 토큰·패딩 포함)
- **값 vs shape** : `input_ids`의 값이 `[4, 12]`인 것과 shape가 `[4, 12]`인 것은 다르다
- **임베딩** : `[B, L]` → `[B, L, D]` — 축이 하나 늘어난다 (`[4, 12]`, D=768 → `[4, 12, 768]`)
- **`padding=True` + `max_length=128`** : 무조건 128칸이 아니다 — 항상 채우려면 `padding="max_length"`
- **선택적 키 처리** : `batch.items()` 순회 또는 `if "token_type_ids" in batch` — 없는 키를 만들지 않는다

</details>
