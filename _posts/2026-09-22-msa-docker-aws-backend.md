## 1. 📖 개요

AWS에서 백엔드 서버를 운영할 때 MSA와 Docker가 각각 어떤 역할을 하는지 정리한다.
또한 `requirements.txt`, `Dockerfile`, `compose.yaml`이 서로 어떻게 연결되는지 살펴보고,
카카오 로그인과 결제 기능을 포함한 백엔드 과제의 전체 흐름을 파악한다.

```text
백엔드 소스 코드
    ↓
requirements.txt로 Python 패키지 버전 기록
    ↓
Dockerfile로 애플리케이션 실행 환경을 이미지로 만듦
    ↓
compose.yaml로 여러 컨테이너를 함께 실행하고 연결
    ↓
AWS 서버에서 컨테이너 실행
```

> 💡 **먼저 구분하기** · MSA는 서비스를 어떻게 나눌지에 관한 아키텍처이고,
> Docker는 나눈 서비스를 일정한 환경에서 실행하는 방법이다.
{: .prompt-tip }

## 2. 🧩 MSA란?

MSA는 **Microservices Architecture**의 약자다. 하나의 큰 애플리케이션을 여러 개의 작은
서비스로 나누고, 각 서비스를 독립적으로 실행하거나 배포할 수 있도록 구성하는 방식이다.

예를 들어 하나의 백엔드에 다음 기능이 있다고 가정한다.

```text
회원 서비스
주문 서비스
결제 서비스
알림 서비스
```

하나의 애플리케이션으로 모두 묶을 수도 있지만, MSA에서는 기능의 책임에 따라 서비스를
분리할 수 있다.

```text
사용자 요청
    ↓
회원 서비스 ── 주문 서비스 ── 결제 서비스
                         └── 알림 서비스
```

### MSA를 사용하는 이유

- 특정 서비스에 문제가 생겼을 때 장애 범위를 줄일 수 있다.
- 필요한 서비스만 수정하거나 배포하기 쉬워질 수 있다.
- 사용량이 많은 서비스만 별도로 확장할 수 있다.

다만 서비스를 나눴다고 해서 장애가 자동으로 막히는 것은 아니다. 주문 서비스가 결제 서비스에
의존하고 있다면 결제 서비스의 장애가 주문 과정에도 영향을 줄 수 있다. 따라서 서비스 분리와 함께
다음과 같은 운영 방법을 생각해야 한다.

- 서비스의 상태를 확인하는 Health Check
- 실패한 컨테이너나 서비스를 다시 실행하는 복구 방식
- 오류와 상태를 확인하기 위한 로그와 모니터링
- 다른 서비스가 응답하지 않을 때의 예외 처리

> 📌 MSA의 목적은 단순히 서버를 많이 띄우는 것이 아니라 **기능별 책임을 나누고 장애와 배포의
> 범위를 관리하는 것**이다.
{: .prompt-info }

## 3. 🐳 Docker의 역할

Docker는 애플리케이션과 실행에 필요한 환경을 **이미지**로 만들고, 그 이미지를
**컨테이너**로 실행할 수 있게 해준다.

```text
Dockerfile
    ↓ build
Docker Image
    ↓ run
Docker Container
```

개발자의 컴퓨터와 AWS 서버의 환경이 달라도 같은 Docker Image를 사용하면 같은 실행 환경을
재현하기 쉬워진다.

### Image와 Container 구분하기

| 구분 | 의미 |
| --- | --- |
| Docker Image | 애플리케이션 실행 환경을 담은 실행 전 설계도 |
| Docker Container | Image를 실제로 실행한 상태 |

하나의 Image를 이용해 여러 개의 Container를 실행할 수도 있다.

## 4. 📁 Docker 관련 파일의 역할

### `requirements.txt`

Python 백엔드에서 사용하는 패키지와 버전을 기록하는 파일이다.

```text
fastapi==버전
uvicorn==버전
```

버전을 정확하게 적으면 개발 환경과 배포 환경에서 서로 다른 버전이 설치되어 동작이 달라지는
문제를 줄일 수 있다.

> ⚠️ 실제 버전은 프로젝트에서 확인한 값으로 작성해야 한다.
{: .prompt-warning }

### `Dockerfile`

Docker Image를 어떻게 만들지 순서대로 작성하는 파일이다. 일반적으로 다음과 같은 내용을 담는다.

1. 어떤 기본 실행 환경을 사용할지 정한다.
2. 애플리케이션 파일을 이미지 안으로 복사한다.
3. `requirements.txt`의 패키지를 설치한다.
4. 서버를 시작할 명령을 지정한다.

즉, `Dockerfile`에는 **서버를 실행하기 위해 필요한 준비 과정과 실행 정보**를 기록한다.

### `compose.yaml`

여러 Container를 한 번에 실행하고 연결하기 위한 설정 파일이다.

```text
compose.yaml
├── backend container
├── database container
└── 필요한 다른 container
```

각 서비스에서 사용할 Image, Port, 환경 변수, Volume, Network와 서비스 간 의존 관계 등을
한곳에서 관리할 수 있다.

### 세 파일의 관계

```text
requirements.txt
    └── Python 패키지와 버전

Dockerfile
    └── requirements.txt를 사용해 Backend Image 생성

compose.yaml
    └── Backend Image와 다른 서비스를 Container로 함께 실행
```

## 5. ☁️ AWS에서는 무엇을 하는가?

AWS는 만든 백엔드와 Docker Container를 실제 서버 환경에서 실행할 수 있는 인프라를 제공한다.
이번 학습 내용에서 역할을 구분하면 다음과 같다.

| 대상 | 해결하려는 문제 |
| --- | --- |
| MSA | 백엔드 기능을 어떤 서비스 단위로 나눌 것인가? |
| Docker | 각 서비스를 어떤 동일한 환경에서 실행할 것인가? |
| AWS | 서비스를 어느 서버 환경에서 운영할 것인가? |

세 가지는 같은 개념이 아니라 서로 다른 문제를 해결하며 연결된다.

## 6. 🛠️ 과제: 원하는 백엔드 서버 구축하기

과제에서는 원하는 백엔드 서버를 만들고 카카오 로그인을 구현한다. 결제 시스템을 만드는 경우에는
토스페이먼츠를 참고한다.

### 카카오 로그인 흐름

카카오 로그인은 사용자가 카카오 계정으로 인증한 결과를 백엔드 서비스의 로그인과 연결하는
과정으로 이해할 수 있다.

```text
1. 사용자가 카카오 로그인 요청
2. 카카오에서 사용자 인증과 동의 진행
3. 인증 결과가 백엔드로 전달됨
4. 백엔드가 카카오의 사용자 정보를 확인
5. 서비스의 회원 정보와 연결
6. 서비스 로그인 상태 생성
```

카카오가 사용자를 인증하는 과정과, 우리 서비스가 로그인 상태를 관리하는 과정은 구분해서
생각해야 한다.

### 토스페이먼츠를 사용하는 경우

결제 시스템을 구현한다면 결제 요청만 보내는 것으로 끝나지 않는다. 백엔드에서는 주문 정보와
결제 결과가 맞는지 확인하고, 성공과 실패에 따라 서비스의 상태를 처리해야 한다.

```text
사용자 결제 요청
    ↓
결제 진행
    ↓
백엔드에서 주문 정보와 결제 결과 확인
    ↓
결제 성공 또는 실패 처리
```

결제에 사용하는 비밀 정보는 클라이언트에 노출하지 않고 백엔드에서 관리해야 한다.

## 7. 🪜 과제를 진행할 때 확인할 순서

1. 만들 백엔드 서비스의 목적을 정한다.
2. 어떤 기능이 필요한지 나눈다.
3. 처음부터 MSA가 필요한지, 하나의 백엔드로 시작해도 되는지 판단한다.
4. 필요한 Python 패키지와 버전을 `requirements.txt`에 기록한다.
5. `Dockerfile`로 백엔드 실행 환경을 만든다.
6. 여러 서비스가 필요하면 `compose.yaml`로 함께 실행한다.
7. 카카오 로그인 흐름을 백엔드와 연결한다.
8. 결제가 필요하면 토스페이먼츠의 결제 흐름을 연결한다.
9. AWS 환경에서 실행하고 로그와 서비스 상태를 확인한다.

## 8. ✅ 핵심 정리

- MSA는 백엔드 기능을 서비스 단위로 나누는 아키텍처다.
- Docker는 서비스를 같은 실행 환경에서 동작하게 만드는 방법이다.
- AWS는 백엔드와 Container를 실제로 운영할 서버 환경을 제공한다.
- 서비스를 나누는 것만으로 안정성이 자동으로 보장되지는 않는다.
- `requirements.txt`, `Dockerfile`, `compose.yaml`은 패키지 → Image → Container 실행 순서로 연결된다.
- 카카오의 사용자 인증과 우리 서비스의 로그인 상태 관리는 구분해서 생각한다.
- 결제 결과는 백엔드에서 주문 정보와 함께 확인해야 한다.
